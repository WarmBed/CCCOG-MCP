## 1. Goal, requirements, and non-goals

### 1.1 Goal

CCCOG-Bar is a resident Windows desktop utility that answers, at a glance:

1. which session is controlling which other session;
2. what task is moving across each dispatch/PATH A edge; and
3. how many input/output/cache tokens and how much cost are attributable to
   each session and edge.

The primary view is a live control-flow graph.  Nodes are provider sessions
(`claude`, `claude-child`, `codex`, and `grok`); edges are dispatches or PATH A
owner relationships.  An edge displays a bounded task summary from
`prompt.txt` and a state animation (`queued`, `running`, `succeeded`, `failed`,
or stale/unknown).

All inputs are local, read-only files.  The bar never sends a provider request,
starts a provider process, changes an owner lease, or mutates a CCCG job.

### 1.2 Mandatory requirements

1. **Performance first.**  Use incremental file observation, bounded parsing,
   coalesced refreshes, and a graph layout that runs only when topology changes.
   The shell must remain responsive while large provider histories are parsed.
2. **Relationship graph.**  Correlate `jobs/*/status.json`, `owners/*.json`,
   `inbox.jsonl`, and provider session files into deterministic node/edge
   snapshots.  Preserve uncertainty explicitly when old data cannot identify a
   caller session.
3. **Bounded, escaped task text.**  Read only a small first-line summary from
   `prompt.txt`, strip the CCCG header, replace control characters, and cap the
   rendered UTF-8 length.  Treat all transcript/prompt/audit content as
   untrusted data, never as instructions.
4. **Usage and cost attribution.**  Parse per-message usage locally.  Codex
   rollout records may provide input, output, cache, and provider-reported cost;
   Claude and Grok adapters must surface missing cost as `unknown` rather than
   silently invent a number.  Aggregate by node and by edge without double
   counting.
5. **Caller identity gap fix.**  Add an optional `callerLabel` argument to
   `cccg_dispatch` and `cccg_dispatch_wait` in the next Host schema batch.  The
   value is passed through the worker/runner, stored in the job, and included in
   the audit record.  Omitting it remains fully backward compatible; old jobs
   continue to use `hopSource`/`hopChain` with an explicit ambiguous identity
   marker.
6. **No dispatch availability regression.**  A bar crash, parse error, or
   unavailable Rust DLL must not block the existing worker/Host path.

### 1.3 Non-goals

- No new remote API, provider API call, billing transaction, quota decision, or
  provider process launch.
- No attempt to reconstruct prompt bodies or expose complete transcripts in the
  UI.  The bar shows only bounded summaries and aggregate usage.
- No claim that `callerLabel` is an authenticated identity.  It is a caller
  supplied display label and must be escaped/bounded; hop guards remain the
  security boundary.
- No rewrite of existing peer discovery, archive semantics, transcript tools,
  or OwnerDaemon behavior beyond the additive `callerLabel` plumbing required
  for graph attribution.
- No requirement to make WinUI, egui, and Tauri simultaneously supported.  One
  shell is selected below; the alternatives are recorded for a deliberate
  fallback.

## 2. Repository and data-format verification

### 2.1 CCCG files that are the source of truth

The following formats were inspected in the current checkout.  The bar reads
them with sharing that permits the worker to continue writing and tolerates a
partially written final line/file.

| Source | Current fields/use | Bar handling |
| --- | --- | --- |
| `%LOCALAPPDATA%\CCCG\dispatch\jobs\*\status.json` | `jobId`, `provider`, `sessionId`, `requestedSessionId`, `cwd`, `model`, `reasoningEffort`, `hopCount`, `hopSource`, `hopChain`, `action`, `status`, `reason/error`, `createdAt/startedAt/finishedAt`, owner/receipt fields | Additive nullable `callerLabel`; parse unknown/old fields safely; use job id as the stable edge id. |
| `jobs\*\prompt.txt` | Header `[CCCG dispatch from Claude Desktop to <provider>]` followed by the prompt | Read a bounded prefix/first meaningful line only; strip the generated header; escape and label as untrusted. Never log or retain the raw prompt. |
| `%LOCALAPPDATA%\CCCG\dispatch\owners\*.json` | `schemaVersion`, `provider`, `sessionId`, `cwd`, `ownerPid`, `spoolDir`, `startedAt`; a live `.lock` lease denotes PATH A ownership | Build a live/stale owner edge; never infer liveness from JSON alone when the lease/process check says stale. |
| `%LOCALAPPDATA%\CCCG\dispatch\inbox.jsonl` | `id`, `fromRole/fromProvider/fromSessionId`, `toRole/toProvider/toSessionId`, `content`, `status`, `jobId`, `createdAt` | Stream lines, tolerate a torn last line, use audit content only as metadata, and never execute or expand it as a prompt. |
| Provider session stores | Codex rollout JSONL; Claude project JSONL; Grok local session/summary/event files | Adapter per provider, bounded incremental cursor, stable message dedup key, and explicit `unknown` for absent usage/cost. Archived paths are ignored. |

`status.json`, owner JSON, and inbox entries may be missing or from an older
schema.  Every parser returns a diagnostic and continues with the rest of the
snapshot; a malformed one-file record cannot erase a previously valid graph.

### 2.2 Caller identity and hop semantics

`hopSource` currently identifies a user/machine (for example,
`user:<user>@<machine>`), not the Claude/Codex session that initiated the
dispatch.  The next dispatch schema batch adds:

```text
callerLabel?: string
```

Contract:

- trim surrounding whitespace, reject/control-replace invalid characters, and
  cap at 128 UTF-8 bytes before persisting;
- an omitted/blank value is `null`, not a fabricated identity;
- `DispatchRunner.Enqueue/Dispatch`, `DispatchJob`, and the worker argument
  path carry it unchanged after normalization;
- `status.json` stores `callerLabel` as a nullable additive field;
- hop/audit creation includes `caller=<bounded label>` when present, without
  copying the prompt; the existing audit envelope and `InboxMessage` JSON shape
  remain readable by old clients;
- the graph uses `callerLabel` as the display/source node key and marks it
  `display-only`; when absent it falls back to `hopChain`/`hopSource` and marks
  the source `ambiguous`.

Rollout order is mandatory: worker accepts and persists the optional field
first; then install the rebuilt Worker; then install the Host with the additive
MCP schema; finally reconnect the Host once.  Existing Hosts and callers that
omit the field continue to work during and after the transition.

### 2.3 Provider usage facts and pricing policy

The TokenBar reference checkout was inspected.  Its vendored `tokscale-core`
already provides provider session parsers, deduplication, aggregation, and a
cached LiteLLM/OpenRouter pricing layer; its Rust FFI exposes JSON-friendly
reports to a WinUI shell.  CCCOG-Bar may reuse that code only through a pinned,
reviewed path dependency or a clearly documented adapter boundary; it must not
copy an unreviewed parser wholesale.

The normalized internal record is:

```text
UsageSample {
  provider, sessionId, messageKey, timestamp, model,
  inputTokens, outputTokens, cacheReadTokens, cacheWriteTokens,
  costMicroUsd: Option<u64>, costSource, sourcePath, sourceOffset
}
```

`costSource` is `provider_reported`, `priced_from_pinned_table`, or `unknown`.
The implementation chooses **integer micro-USD (`u64`)** rather than `f64` or a
Rust `decimal` type: money is never represented by a binary floating-point
number, the wire format is deterministic, and the display can round only at the
final presentation boundary.  The core README must document this choice and
the conversion/overflow rules.  An explicit finite provider cost is converted
to micro-USD only with a checked decimal parser and wins over pricing.  A
missing cost may be calculated only when the model and a pinned local price
revision are known; otherwise the UI shows `—`/`unknown` and the diagnostic says
why.  The bar is offline at runtime: any optional price refresh belongs to a
future, separately approved feature.

Adapters must cover at least:

- **Codex:** rollout JSONL message usage including input/output/cache fields
  and any explicit cost; malformed/partial lines are skipped with a diagnostic.
- **Claude:** `~/.claude/projects/<hash>/<sessionId>.jsonl` assistant usage
  variants (`message.usage` and known field aliases), with cost marked unknown
  when no authoritative value or pinned model price exists.
- **Grok:** the locally discovered session/summary/event files and their actual
  usage fields; no estimate is emitted when the provider stores no usage.

The parser cursor is `(path identity, file length, mtime, byte offset)` plus a
stable message hash.  Truncation/rewrites reset the cursor safely.  A message is
counted once even if it appears in a polling snapshot, and a failed/queued job
does not acquire provider usage that has not occurred.

## 3. Technical selection: Rust core and Windows shell

### 3.1 Options

| Option | Performance/native integration | Maintenance cost | Decision |
| --- | --- | --- | --- |
| **Rust core + WinUI 3 shell** | Native Windows window/tray, DPI, topmost/flyout, animations, and low-overhead FFI; Rust is well suited to bounded file parsing and aggregation. | Two toolchains and a small C ABI/JSON DTO boundary; WinAppSDK packaging and Windows-specific testing are real costs. Existing TokenBar-Windows demonstrates this shape. | **Recommended.** Keep the shell thin and keep all parsing/graph math in Rust. |
| Rust core + egui/eframe | One Rust application and cheap custom graph drawing; no managed/native bridge. | Tray, activation, accessibility, text/DPI polish, native window behavior, and Windows packaging require bespoke work; less consistent with the requested desktop bar feel. | Viable fallback if WinUI build/packaging blocks the project, not first choice. |
| Rust core + Tauri | Fast web UI iteration and mature WebView2 shell integration. | WebView2 memory/startup/bridge overhead, two UI runtimes, and more attack/privacy surface for untrusted prompt text; less attractive for an always-on low-footprint bar. | Not recommended for the performance-first bar. |

### 3.2 Recommendation and performance contract

Use a Rust workspace under `bar/` with a pure `cccog-bar-core` crate and a
small `cccog-bar-ffi` `cdylib`.  The WinUI 3 app under `bar/app/` consumes one
versioned JSON snapshot per refresh through the C ABI, following the proven
TokenBar pattern.  The app owns only window/tray/input/rendering state.

Initial measurable targets (fixtures are part of the tests, not a claim about
all machines):

- parse and aggregate a fixture with 5,000 job directories and 100 provider
  sessions in <=2 seconds cold and <=250 ms for a single changed job after the
  first snapshot;
- coalesce filesystem events for 100–250 ms, keep idle CPU below 1% on a
  1-second observation interval, and avoid rereading unchanged bytes;
- layout topology only when nodes/edges change; animate status changes at a
  bounded 30/60 fps without reparsing files;
- keep the shell responsive during cold parse, with a stale/“updating” badge;
- use release LTO/stripped native binaries and explicit x64/ARM64 build gates.

These are acceptance thresholds to measure and tune, not permission to weaken
correctness or privacy bounds.

## 4. Graph, attribution, and privacy model

### 4.1 Normalized snapshot

The Rust core publishes a versioned `GraphSnapshot`:

```text
GraphSnapshot {
  generatedAt, sourceRevision, diagnostics[], truncated,
  nodes: Node[], edges: Edge[], totals: UsageTotals
}

Node { id, provider, sessionId?, label, kind, state, startedAt?, updatedAt?, usage }
Edge { id, kind, sourceNodeId, targetNodeId, jobId?, taskSummary,
       status, createdAt?, finishedAt?, usage, identityConfidence }
```

Node ids are stable `(provider, sessionId)` where a real session is known.
Caller labels without a session id use a namespaced synthetic id and are never
silently merged with a real provider session.  `claude-child` is a distinct
kind, even if its provider is Claude.

Edge kinds:

- `dispatch`: job source (callerLabel or ambiguous hop source) to the selected
  provider/session;
- `path_a_owner`: owner process/session to the provider session described by a
  live owner registration;
- `audit_hint`: optional metadata-only edge when an inbox audit links records
  that are not yet represented by a job; it is visibly lower confidence and
  never replaces a job edge.

Jobs with no `sessionId` target a stable requested-session node until a later
status update resolves it.  Stale owner leases, archived paths, malformed
records, and missing provider files become diagnostics/badges, not invented
edges.  Cycles are rendered as data (with a hop/status badge); the bar does not
attempt to “fix” the dispatch graph.

### 4.2 Task summary safety

The core reads at most a small configured prefix (default 4 KiB) of each
`prompt.txt`, removes the generated dispatch header, selects the first line,
replaces CR/LF/control characters with visible escapes, and emits at most 160
UTF-8 bytes (with an ellipsis marker).  The shell applies a second display cap
and never offers a “show raw prompt” action.  Diagnostics contain path and
reason, not prompt contents.  Tests include secrets, ANSI/control sequences,
newlines, invalid UTF-8, and instruction-like text to prove data is inert.

### 4.3 Usage attribution

- Node usage is the deduplicated sum of usage samples belonging to that
  provider/session.
- A job edge receives samples from its target session after the job's
  `startedAt` and until `finishedAt` (or the current snapshot for a running
  job).  Samples that cannot be temporally/session-bound stay in the node total
  and are marked unallocated rather than counted on every edge.
- A PATH A edge receives owner-session samples in its live ownership interval;
  overlapping intervals are flagged instead of double-counted.
- `callerLabel` disambiguates the source display node; it does not change token
  totals or grant trust.  Old jobs use hop-chain fallback and show “caller
  unknown/ambiguous”.
- Totals expose input, output, cache-read, cache-write, and cost separately.
  Provider-reported, pinned-estimated, and unknown cost are visually distinct.

## 5. Data flow and planned file layout

### 5.1 Read-only data flow

1. A debounced watcher/poller observes the dispatch root and provider session
   roots.  It records path/mtime/length changes and queues bounded parse work.
2. Rust adapters read status, prompt prefix, owners/leases, inbox JSONL, and
   provider usage streams.  Archive subtrees are excluded, matching the
   existing parity-tool visibility rule.
3. The graph reducer normalizes identities, resolves job/owner/audit links,
   deduplicates usage, and emits diagnostics plus one immutable snapshot.
4. The FFI returns the snapshot as versioned UTF-8 JSON (or a compact binary
   envelope later if profiling proves JSON is the bottleneck).
5. WinUI renders nodes/edges, status animation, bounded task labels, usage
   badges, filters, and a stale/update indicator.  It never reads or interprets
   prompt text itself.

### 5.2 New `bar/` workspace

```text
bar/
  Cargo.toml                         # workspace; release LTO/strip settings
  crates/
    cccog-bar-core/
      src/{lib,dispatch,owners,inbox,providers,usage,graph,pricing,privacy}.rs
      tests/                          # hermetic Rust fixtures and property tests
    cccog-bar-ffi/
      src/lib.rs                      # versioned C ABI/JSON snapshot envelope
      include/cccog_bar.h
  app/
    CCCOG.Bar.App/                   # thin WinUI 3 unpackaged shell
      CCCOG.Bar.App.csproj
      GraphView/, Tray/, Interop/, ViewModels/
  fixtures/
    dispatch/{jobs,owners,inbox.jsonl}/
    providers/{codex,claude,grok}/
  README.md                           # build/install/rollback and privacy notes
```

The app is a separate Windows project (targeting the repo's supported .NET 8
plus a pinned Windows App SDK) and is not added to the broken solution.  A
future build integration may add explicit project targets, but the .NET CCCG
worker/Host build remains independently runnable.  The Rust core must have no
WinUI dependency so its parser/graph tests run on CI and on a developer host.

### 5.3 Existing CCCG files touched by the callerLabel slice

The later implementation may change only these additive paths (plus focused
tests/docs named by the implementation wave):

- `src/CCCG.Core/Dispatch/DispatchJob.cs` — nullable normalized field and JSON
  compatibility;
- `src/CCCG.Core/Dispatch/DispatchRunner.cs` — optional argument plumbing and
  audit display metadata;
- `src/CCCG.Dispatch/DispatchTools.cs` — optional Host schema parameter on
  `cccg_dispatch` and `cccg_dispatch_wait`, included in invoke payload;
- `src/CCCG.Dispatch.Worker/Program.cs` — read/forward optional argument;
- focused `tests/CCCG.Tests` files for old/new payloads, persistence, and audit.

No provider command, hop arithmetic, quota behavior, archive behavior, or
existing required field name is changed by this feature.

## 6. TDD test plan (strict red -> green order)

Every item is written first with a failing assertion, then the smallest code
needed to make it pass.  Fixtures are synthetic and must not contain real
prompts, tokens, or user paths.

### Wave 0 — contracts, fixtures, and callerLabel red tests

1. Core fixture loader rejects a path outside the configured roots and ignores
   `cccg-archive` descendants.
2. A status fixture containing `callerLabel` round-trips; an old fixture with
   no field round-trips byte-compatible defaults.
3. Whitespace/overlong/control-containing labels normalize to the specified
   bounded value; blank becomes `null`.
4. Host invoke payload includes the optional label; an old payload omitting it
   remains accepted.
5. Worker/runner forwards the label into `DispatchJob` and the audit content;
   audit contains no prompt text.

### Wave 1 — pure parsers and privacy bounds

6. Status parser handles queued/running/succeeded/failed, missing optional
   fields, invalid timestamps, and unknown JSON fields deterministically.
7. Prompt summary strips the generated header, selects the first line, escapes
   controls/invalid bytes, truncates at the UTF-8 boundary, and proves secret or
   instruction-like text is not returned beyond the configured cap.
8. Owners parser creates a PATH A edge only for a live lease/process; stale or
   malformed owner files become diagnostics.
9. Inbox parser handles valid lines, malformed lines, and a torn final line;
   audit links use bounded metadata only and never parse content as commands.
10. Archive exclusion holds for jobs, owners, inbox-linked paths, and all three
    provider roots.

### Wave 2 — provider usage, pricing, and incremental behavior

11. Codex fixture parses input/output/cache tokens and explicit cost per
    message; Claude fixture parses known assistant usage variants; Grok fixture
    with no usage returns unknown, not zero-cost evidence.
12. Malformed/partial provider lines are skipped while valid neighboring lines
    remain visible; diagnostics identify file/offset only.
13. Duplicate polling snapshots and repeated message ids count once; a
    truncate/rewrite resets the cursor without double counting.
14. Explicit provider cost wins over pricing; a pinned local price calculates a
    clearly estimated cost; unknown model/rate yields `unknown`.
15. Incremental scan reads only changed bytes/tail windows and stays under the
    configured work cap; a large nominal file does not exhaust the budget when
    only a bounded window is read.

### Wave 3 — graph reduction and attribution

16. A labeled dispatch produces the expected caller/source node, target node,
    task summary, status, and edge identity.
17. A legacy unlabeled dispatch uses hop-chain/source fallback and sets
    `identityConfidence=ambiguous` rather than merging unrelated sessions.
18. PATH A owner registration produces an owner edge and stale lease removal
    removes it on the next snapshot.
19. Jobs resolving from requested session to actual session update one stable
    edge, not two; repeated audit messages deduplicate.
20. Cyclic hop data renders as a finite graph with a cycle diagnostic; no
    recursive traversal can hang or allocate without a bound.
21. Direct dispatch, child dispatch, and PATH A usage are attributed to the
    correct edge/node interval; failed/queued jobs do not receive unobserved
    usage; unallocatable samples are counted once at node level.
22. Node and edge totals preserve input/output/cache/cost dimensions and
    distinguish provider-reported, estimated, and unknown cost.

### Wave 4 — refresh, FFI, and shell contract

23. File watcher bursts coalesce into one snapshot generation; a torn status or
    inbox write never publishes a partially reduced graph.
24. Snapshot JSON schema is versioned, deterministic in node/edge order, bounded
    in size, and includes diagnostics/truncation status.
25. FFI invalid input returns a structured error without crashing or mutating
    CCCG files; repeated calls release all native allocations.
26. Rust core cold/incremental performance fixtures meet §3.2 targets and
    prove unchanged files are not reread.

### Wave 5 — WinUI acceptance checklist (implementer self-check + user final acceptance)

The visual, accessibility, DPI, and long-soak items below are not claimed as
independently verifiable by the reviewer through Rust/FFI tests alone.  The
implementer must attach a self-check record (screenshots/logs where useful),
and the user performs the final acceptance on the installed Windows shell.
The independent gate for this project covers the Rust core/FFI tests, real
dispatch-file snapshot correctness, and callerLabel end-to-end behavior.

27. Tray launch, close-to-tray, reconnect/restart, and missing-core-DLL states
    are recoverable; bar failure never affects the worker.
28. Graph nodes/edges, task labels, state animation, unknown/stale badges,
    provider filters, and node/edge usage/cost tooltips match the snapshot.
29. Prompt/audit text is visibly escaped and bounded; no raw prompt, secret, or
    instruction can be expanded from the UI.
30. Topmost/flyout behavior, keyboard navigation, screen reader names, focus,
    dark/light mode, x64/ARM64, and 100/150/200% DPI are accepted.
31. A 60-minute file-churn soak meets idle CPU/memory/refresh targets and
    recovers from provider file rotation, archive moves, malformed records, and
    worker restart.

The implementation gate is **136 + all Wave 0–5 tests green**, with individual
.NET project builds and the Rust core/FFI/shell release builds reporting zero
errors.  UI checklist failures are not hidden by a passing parser test.

## 7. Compatibility, rollout, and reconnect

- Existing dispatch remains file/API compatible.  `callerLabel` is nullable and
  additive; old status readers ignore it and old Hosts omit it.
- Worker-first rollout: build/test/install the worker and verify old Host calls;
  then install the Host schema containing the optional argument; reconnect once
  so the MCP tool list refreshes.  No reconnect is needed for the read-only bar
  itself if it is shipped separately.
- The bar reads a snapshot and does not hold exclusive locks.  If a source is
  absent, it shows “not discovered” and keeps the last valid graph with a stale
  badge.  It never writes a repair file or deletes an archive.
- A caller label is display metadata, not authentication.  Existing hop-count,
  fail-closed, quota, and audit guardrails remain authoritative.

## 8. Risks and rollback

| Risk | Mitigation | Rollback signal/action |
| --- | --- | --- |
| Provider session format drifts | Versioned adapters, fixtures from observed local shapes, diagnostics, unknown cost fallback | Disable the affected adapter; keep other nodes and last snapshot. |
| Usage double counting | Stable message keys, cursor/mtime state, interval attribution tests | Drop only the affected usage cache and rebuild from source; never edit provider files. |
| LiteLLM/pinned prices stale | Show price revision and `estimated`; preserve provider-reported cost | Disable estimation and display unknown until a reviewed table is shipped. |
| Prompt/audit privacy leak | Prefix/first-line/UTF-8 caps, escaping, no raw UI path, synthetic fixtures | Turn off task labels while retaining graph/usage; delete only bar-local cache. |
| File churn or partial writes | Debounce, shared reads, atomic snapshot publication, bounded queues | Pause refresh and keep last good snapshot; dispatch continues. |
| WinUI/FFI packaging or architecture failure | Thin shell, pure Rust core, x64/ARM64 gates, separate project | Ship core/CLI diagnostics or remove only `bar/`; do not block .NET builds. |
| Caller label spoofing/confusion | Bounded display-only label and explicit confidence badge; hop guard unchanged | Ignore labels and fall back to hop source while preserving jobs/audits. |

Rollback is additive and reversible: uninstall/disable the bar, remove its
bar-local cache, and restore the previous Worker/Host binaries if the
callerLabel slice causes a dispatch regression.  Existing job/status fields,
archives, quotas, and inbox history are preserved; no rollback step deletes
provider session data.
